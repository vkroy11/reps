# Deploying Reps

Three pieces, in this order: **database → API → web app**. Each one needs the
URL of the one before it.

| Piece    | Host   | Why                                                             |
| -------- | ------ | --------------------------------------------------------------- |
| Postgres | Neon   | Free tier does not expire, so the deploy still works next month |
| API      | Render | Blueprint in the repo, free Node service                        |
| Web app  | Vercel | Static export, per-route HTML, edge-cached                      |

Android APK is separate — see [EAS](#android-apk) at the end.

---

## 1. Postgres on Neon

1. <https://neon.com> → sign in → **New project**.
2. Name it `reps`. Pick the region closest to the Render region you will use
   (the blueprint says `oregon`, so **AWS us-west-2** pairs with it). Every API
   request pays this round trip, twice on writes.
3. Copy the **pooled** connection string from the dashboard. It looks like:

   ```
   postgresql://USER:PASSWORD@ep-xxx-pooler.us-west-2.aws.neon.tech/reps?sslmode=require
   ```

   Use the **pooled** one (`-pooler` in the host). Render's free instance
   restarts often, and each restart opens fresh connections; the pooler is what
   stops that exhausting Neon's connection limit.

Nothing else to do here. The API runs `prisma migrate deploy` during its build,
so Neon starts empty and gets its schema on the first deploy.

## 2. API on Render

The repo has [`render.yaml`](render.yaml), so this is a blueprint deploy rather
than a dashboard full of fields. **Commit and push it first** — Render reads it
from the branch.

1. <https://dashboard.render.com> → **New** → **Blueprint**.
2. Connect the GitHub repo (`vkroy11/reps`) and pick branch `main`.
3. Render reads `render.yaml`, shows one service (`reps-api`), and prompts for
   the values marked `sync: false`. Paste:

   | Variable          | Value                              |
   | ----------------- | ---------------------------------- |
   | `DATABASE_URL`    | the Neon pooled string from step 1 |
   | `GROQ_API_KEY`    | from your local `.env`             |
   | `YOUTUBE_API_KEY` | from your local `.env`             |

   `SESSION_SECRET` is generated by Render — leave it alone. Everything else is
   already set in the blueprint.

4. **Apply**. First build is 2–4 minutes.

Then check it:

```bash
curl https://reps-api-a2lg.onrender.com/api/health
# {"status":"ok","uptime":...}
```

Note the real hostname Render gives you — you need it in step 3. Render appends
a suffix when the service name is already taken, which is why this deploy is
`reps-api-a2lg` and not `reps-api`. It has to match in three places: Vercel's
`EXPO_PUBLIC_API_URL`, `eas.json`, and anything you curl.

### What the build does, and why

```
npm ci --include=dev -w @reps/api --include-workspace-root
npm run db:generate:ci -w @reps/api     # prisma generate
npm run db:deploy:ci   -w @reps/api     # prisma migrate deploy
npm run build:api                       # tsup -> one ESM file
```

- **The scoped install is not an optimisation, it is required.** A plain
  `npm ci` installs every workspace, and `apps/mobile` pulls in Expo and React
  Native — 6.3 GB of `node_modules` for a service that needs 373 MB of it. That
  does not fit a free instance. `-w @reps/api --include-workspace-root` still
  links `@reps/core`, because npm resolves the workspace dependencies of the
  workspace you asked for.
- **`--include=dev`** because `prisma` and `tsup` are devDependencies and
  `NODE_ENV=production` would otherwise skip them.
- **Migrations run at build, not at start.** A bad migration then fails the
  deploy while the previous release is still serving, and cold starts stay fast.
  Every migration here is additive, so the schema being one release ahead of the
  code for a few seconds is safe.

### Things to know about the free plan

- **It sleeps after 15 minutes idle.** The next request takes 30–60s while the
  instance wakes. Warn anyone reviewing the deploy, or hit `/api/health` from an
  uptime pinger to keep it warm.
- **No shell access and an ephemeral disk.** Nothing is stored on the instance;
  all state is in Neon.

### If the deploy fails

- `SESSION_SECRET must be set in production` — the generated value did not get
  attached. Add it manually in **Environment**.
- `Can't reach database server` — the Neon string is missing `?sslmode=require`,
  or it is the unpooled host.
- `Cannot find module 'tsup'` — `--include=dev` was dropped from the build
  command.

## 3. Web app on Vercel

The build is `expo export --platform web`, which produces static per-route HTML
in `apps/mobile/dist`. Settings live in [`vercel.json`](vercel.json), so the
dashboard needs almost nothing.

### With the CLI

```bash
npm i -g vercel
vercel login                 # interactive, opens a browser

# From the repo root. Links the directory to a project; answer:
#   Set up and deploy? yes
#   Which scope? your account
#   Link to existing project? no
#   Project name? reps
#   In which directory is your code located? ./          <- repo root, not apps/mobile
vercel

# The API URL has to be present at BUILD time - Expo inlines every
# EXPO_PUBLIC_* variable into the bundle, so setting it later does nothing
# until the next build.
vercel env add EXPO_PUBLIC_API_URL production
# paste: https://reps-api-a2lg.onrender.com

vercel --prod
```

Root directory is the **repo root**, not `apps/mobile`: the build command is a
workspace script and needs the root `package.json` and lockfile.

### Or in the dashboard

<https://vercel.com/new> → import the GitHub repo, then:

| Field            | Value                                             |
| ---------------- | ------------------------------------------------- |
| Framework Preset | **Other**                                         |
| Root Directory   | `./` (leave empty)                                |
| Build Command    | `npm run build:web && npm run verify:web`         |
| Output Directory | `apps/mobile/dist`                                |
| Install Command  | `npm ci -w @reps/mobile --include-workspace-root` |

Then **Settings → Environment Variables**, for Production:

| Variable              | Value                           |
| --------------------- | ------------------------------- |
| `EXPO_PUBLIC_API_URL` | `https://reps-api-a2lg.onrender.com` |

Add it **before** the first build, or redeploy after adding it. `vercel.json`
already supplies the build command, output directory and rewrites, so those
fields are only there for clarity — Vercel takes the file's values.

### The one that will bite you

`EXPO_PUBLIC_*` values are inlined by a Babel transform, and **Metro's
transform cache is not keyed on them**. A build that once ran without
`EXPO_PUBLIC_API_URL` keeps reusing the cached transform — with the branch that
reads it dead-code eliminated — however many times you set it afterwards. The
compiled function ends up as:

```js
// no EXPO_PUBLIC_API_URL when the transform was cached
resolveApiBaseUrl = function () {
  return `http://localhost:${n}`;
};
```

Vercel keeps its build cache between deployments, so this shows up as: set the
variable, redeploy, still get localhost, dashboard looks correct. It is close to
undebuggable from the outside.

Two things guard against it:

- `build:web` runs `expo export --platform web --clear`, so every build starts
  from a cold transform cache.
- `npm run verify:web` reads the built bundle and fails if it does not contain
  the URL it was told to use.

Run it after any build you are about to ship:

```bash
EXPO_PUBLIC_API_URL=https://reps-api-a2lg.onrender.com npm run build:web
EXPO_PUBLIC_API_URL=https://reps-api-a2lg.onrender.com npm run verify:web
# Web build points at https://reps-api-a2lg.onrender.com (1 bundle(s) checked).
```

On Vercel, make it part of the build so a bad bundle never deploys — set the
Build Command to:

```
npm run build:web && npm run verify:web
```

### Why the rewrites exist

Expo exports dynamic routes as literal filenames: `technique/[id].html`. Vercel
would 404 on `/technique/tec_123` without being told they are the same thing:

```json
{ "source": "/technique/:id", "destination": "/technique/[id]" }
```

`/`, `/path`, `/notes`, `/me` and the onboarding steps are real static files and
need no rewrite.

### Check it

Open the deployment and confirm:

- the welcome screen renders (fonts loaded, Pip visible),
- **the onboarding questionnaire completes and builds a path** — this is the
  step that proves the browser can reach the Render API,
- a hard refresh on `/path` still works (static route),
- opening a technique from the path board works (the rewrite).

If the app renders but every request fails, check the Network tab. Requests
going to `localhost:4000` mean the URL never made it into the bundle — see
[the one that will bite you](#the-one-that-will-bite-you) above, and confirm the
Build Command includes `npm run verify:web`.

## Android APK

```bash
cd apps/mobile
eas build --platform android --profile preview
```

`EXPO_PUBLIC_API_URL` has to be in the EAS build environment too — set it in
`eas.json` under the `preview` profile's `env`, or in the EAS dashboard. A build
that inlines `localhost` produces an APK that talks to the phone itself and
fails every request. EAS caches too, so the same transform-cache trap applies.

## The env var map

| Variable                  | Where              | Notes                                                 |
| ------------------------- | ------------------ | ----------------------------------------------------- |
| `DATABASE_URL`            | Render             | Neon pooled string, `?sslmode=require`                |
| `GROQ_API_KEY`            | Render             | Path planning and ranking                             |
| `YOUTUBE_API_KEY`         | Render             | Data API v3, 10k units/day                            |
| `SESSION_SECRET`          | Render             | Generated; required in production                     |
| `AI_PROVIDER`             | Render             | `groq`; blueprint sets it                             |
| `AUTH_PROVIDER`           | Render             | `google`; `fake` is refused in production             |
| `GOOGLE_OAUTH_CLIENT_IDS` | Render             | Optional — sign-in is off without it, app still works |
| `EXPO_PUBLIC_API_URL`     | Vercel **and** EAS | Inlined at build time, not read at runtime            |

Nothing secret belongs in Vercel or EAS: everything the client holds ships in
the bundle, which is why the only variable there is a URL.
